# SALON POKE BY VIVA 預約及套票平台設計規格

日期：2026-09-14

狀態：已獲店主確認

範圍：單一香港店舖的客戶預約、員工排班、套票及管理後台

## 1. 目標

把現有網站由展示型半成品改造成可正式營運的預約平台。完成後：

- 客人可預約服務、指定員工或選擇「任何可服務員工」。
- 系統只顯示符合員工技能、上班時間、休息、請假和既有預約的時段。
- 即使兩名客人同時提交同一時段，資料庫亦只會接受其中一個預約。
- 已登入客人可查看及使用自己的套票，並管理符合規則的預約。
- 管理員可處理預約、客戶、員工、排班、服務、套票及網站設定。
- 所有敏感操作有權限檢查和審計紀錄。

## 2. 已確認的產品決定

- 店舖模型：單一香港店舖，時區固定為 `Asia/Hong_Kong`。
- 員工選擇：客人可指定員工，或由系統分配任何合資格且有空的員工。
- 員工資格：每項服務可分配一位或多位能執行該服務的員工。
- 套票私隱：客人必須登入才可查看及使用自己的套票；不可單靠電話號碼取得套票資料。
- 訪客預約：未登入客人仍可自費預約，但不可使用套票或查看既有客戶資料。
- 價格單位：資料庫以港幣分儲存，介面顯示 `HK$`。
- 套票付款：保留 Stripe 接口，但無正式金鑰時不可偽裝完成付款；管理員仍可手動派發套票。
- 通知：電郵為正式可用渠道；未配置服務時清楚顯示停用，不把 dry-run 當作已發送。
- 語言：主要營運介面使用繁體中文（香港），保留公開網站的中英文能力。

## 3. 不納入本次範圍

- 多分店、房間、儀器容量或 provider group 等企業級資源調度。
- 員工佣金、薪酬、打卡和會計總帳。
- WhatsApp Business API 或 SMS 供應商整合。
- 候補名單、團體預約及同一預約包含多項服務。
- 原生手機 App。

專案內現有 `lib/booking/phase2.js` 和 `lib/booking/availability.js` 屬於另一套未完整移植的多分店資料模型。新系統不會以該模型作為正式預約來源，避免同時維護 `bookings` 與 `appointments` 兩套互相矛盾的資料。

## 4. 整體架構

沿用現有 Next.js App Router、Supabase PostgreSQL、Supabase Auth 和 Vercel：

1. 公開及會員頁面負責收集選擇和呈現狀態。
2. Next.js Route Handlers 驗證輸入、登入狀態和管理員權限。
3. 純函式的 availability domain 計算候選員工及時段，供 API 和測試共用。
4. PostgreSQL RPC 在單一交易內再次驗證時段、分配員工、建立預約和扣減套票。
5. 資料庫 exclusion constraint 作為最後一道競爭條件防線。
6. 成功提交後才產生通知紀錄；通知失敗不會刪除已成立的預約，但後台會顯示失敗狀態。

`appointments` 是唯一預約真相來源。公開可用時段、客戶帳戶和管理後台都讀取這張表。

## 5. 資料模型

### 5.1 員工及服務能力

新增 `staff`：

- `id`
- `name`
- `display_name`
- `bio`
- `colour_hex`
- `is_active`
- `sort_order`
- `created_at`、`updated_at`

新增 `staff_services`：

- `staff_id`
- `service_id`
- 複合唯一鍵 `(staff_id, service_id)`

只有啟用的員工和已分配的服務會出現在客人選擇中。

### 5.2 員工工作時間

新增 `staff_weekly_hours`：

- `staff_id`
- `weekday`，0 至 6
- `is_working`
- `starts_at`
- `ends_at`
- 複合主鍵 `(staff_id, weekday)`

新增 `staff_time_off`：

- `id`
- `staff_id`
- `starts_at`、`ends_at`
- `reason`
- `created_by`
- `created_at`

全店營業時間及 `blocked_dates` 仍是外層限制。員工可用時間必須同時落在店舖營業時間和員工工作時間內，而且不與請假重疊。

午飯或短休息以 `staff_time_off` 的時間範圍表示，無須另一張用途重複的 break 表。

### 5.3 預約

擴充 `appointments`：

- `staff_id`，必須指向 `staff`
- `buffer_minutes`，建立時保存當刻設定
- `occupied_until`，等於服務結束時間加 buffer
- `source`：`web`、`admin` 或 `account`
- `cancelled_at`、`cancelled_by`

啟用 `btree_gist`，對有效狀態的預約建立員工時間排斥限制：同一 `staff_id` 的 `[starts_at, occupied_until)` 不可重疊。`cancelled` 和 `no_show` 不佔用未來時段；`pending`、`confirmed` 和 `completed` 均保留歷史時間完整性。

### 5.4 套票

保留並收斂現有模型：

- `packages`：套票範本、價錢、總次數、有效期和啟用狀態。
- `package_services`：套票適用服務。
- `customer_packages`：已派發或已付款的客戶套票、餘額和到期日。
- `package_redemptions`：每次扣減和退回的不可重複紀錄。

補充規則：

- 套票必須屬於目前登入客戶。
- 套票須啟用、未到期、有餘額，且包含所選服務。
- 同一預約最多扣一次。
- 取消符合規則時最多退一次。
- 預約建立失敗時不扣套票；套票扣減失敗時不建立預約。

### 5.5 客戶帳戶連結

`customers` 增加可選的 `user_id`，以 Supabase Auth 身分綁定客戶記錄。後端只按 `auth.uid()` 查找客戶，不接受瀏覽器傳入任意 `customer_id` 作為所有權證明。

同一正規化電話號碼不自動合併帳戶，以免錯誤合併共用電話；需要合併時由管理員操作並留下審計紀錄。

## 6. 防撞與建立預約交易

建立 `create_appointment_v2` RPC，輸入服務、員工偏好、開始時間、客人資料、可選套票和來源。

交易流程：

1. 鎖定服務設定並驗證服務仍可預約。
2. 驗證日期沒有超出可預約窗口，也不是全店休息日。
3. 建立候選員工清單：啟用、可做該服務、當時上班、沒有請假。
4. 如客人指定員工，只檢查該員工；如選任何員工，按該日有效預約數最少、再按 `sort_order` 和 `id` 排序。
5. 逐一嘗試插入預約；資料庫排斥限制若偵測重疊，嘗試下一位候選員工。
6. 如使用套票，在同一交易鎖定 `customer_packages`，驗證所有權、適用服務、到期日和餘額，再扣減及寫入 redemption。
7. 全部成功才提交交易並回傳預約資料。

前端看到的可用時段只屬提示；提交時必須重新驗證。時段剛被其他人預約時，API 回傳 `409 slot_unavailable`，介面刷新時段並保留其他已填資料。

管理員新增或改期預約亦使用同一套資料庫規則，除非明確選擇「強制安排」。第一版不提供強制重疊，避免誤操作破壞防撞保證。

## 7. 可用時段規則

後台可設定：

- 全店每週營業時間。
- 全店休息日期範圍。
- 每位員工每週上班時間。
- 員工指定日期及時間的休假／休息。
- 全店預約 buffer，預設 15 分鐘。
- 時段間隔，預設 30 分鐘。
- 最早可預約提前時間，預設 2 小時。
- 最遠可預約日數，預設 90 日。
- 取消期限，預設開始前 24 小時。

某時間只有在至少一位合資格員工可以完整容納「服務時長＋buffer」時才顯示。指定員工時只顯示該員工的空檔；選任何員工時顯示合資格員工時段的聯集。

所有日期邏輯都以香港時間計算，資料庫仍以 `timestamptz` 儲存。

## 8. 客人流程

### 8.1 預約精靈

把現有單一長表單改為手機優先的分步流程：

1. 選擇服務。
2. 選擇員工或「任何可服務員工」。
3. 選擇日期和可用時間。
4. 登入／確認聯絡資料；已登入者可選適用套票。
5. 預覽服務、員工、時間、價錢或套票扣減，確認條款後提交。
6. 顯示預約編號、加入日曆及管理預約入口。

登入客人的姓名、電話和電郵由帳戶預填。訪客只建立新的預約聯絡資料，不會獲得其他客戶資料。

### 8.2 我的帳戶

- 顯示即將進行和過往預約。
- 顯示套票總次數、剩餘次數、到期日和使用紀錄。
- 在取消期限前取消並自動退回套票次數。
- 改期時使用同一防撞程序；成功取得新時段才釋放舊時段。
- 修改姓名、電話和電郵。

## 9. 管理後台

後台改為獨立路由或清楚分區，避免所有功能塞在一個大型 client component：

- 營運首頁：今日預約、待確認、即將到期套票及通知失敗。
- 預約日曆：日／週檢視、搜尋、建立、改期、確認、完成、取消和 no-show。
- 客戶：資料、預約歷史、套票及備註。
- 員工與排班：員工 CRUD、可做服務、每週更表、休息及請假。
- 服務：名稱、說明、時長、價格、發佈狀態及可服務員工。
- 套票：範本、適用服務、派發、調整餘額和停用。
- 網站內容：品牌、聯絡方式、地址、WhatsApp、首頁內容。
- 系統設定：營業時間、預約規則、取消規則及通知狀態。
- 管理員及審計：邀請／停用管理員、查看操作紀錄。

所有管理員寫入 API 必須重新驗證目前使用者是有效管理員，通過輸入驗證和 rate limit，並寫入包含 before／after 的審計紀錄。

## 10. 權限與私隱

- 前端只使用 Supabase publishable／anon key；service-role key 只存在伺服器。
- 所有 `public` schema 新表啟用 RLS，並明確設定 Data API 所需權限。
- 公開使用者只可讀取已發佈服務、可公開員工資料及不含私人原因的可用時段結果。
- 客人只可讀取以 `auth.uid()` 綁定的客戶、預約、套票和 redemption。
- 管理員 Route Handler 使用伺服器端 client，並逐次驗證 `admin_users.is_active`。
- 公開 API 不回傳客戶搜尋結果、套票餘額、私人員工請假原因或其他客人的預約資料。
- 預約確認頁不可只憑連續數字 ID 顯示私人資料；使用不可猜測的管理 token 或要求登入。

## 11. 錯誤處理

API 使用穩定錯誤代碼和繁體中文訊息：

- `slot_unavailable`：時段剛被預約。
- `staff_unavailable`：指定員工不能提供該服務或當時不在班。
- `package_not_usable`：套票無效、過期、餘額不足或不適用。
- `authentication_required`：此操作必須登入。
- `booking_window_invalid`：日期太近、太遠或已過去。
- `validation_error`：欄位格式錯誤。

可恢復錯誤保留表單選擇並提供重試；不可恢復錯誤回到相應步驟。伺服器記錄技術詳情，但不向客人洩漏資料庫訊息或金鑰。

## 12. 介面與內容品質

- 全站手機優先，按鈕和表單符合觸控尺寸。
- 預約步驟有清晰進度、載入、空狀態、錯誤和成功狀態。
- 後台統一使用繁體中文和 `HK$`，清除目前殘留的英文、英鎊和舊品牌字眼。
- 移除 `852XXXXXXXX`、`待提供`、假地址及示意圖等佔位內容；缺少正式資料時隱藏相關連結，不展示假資料。
- 表單有正確 label、鍵盤操作、焦點狀態和 `aria-live` 訊息。
- 內部導航使用 Next.js `Link`，圖片使用 `next/image` 或有合理例外說明。

## 13. 測試策略

### 單元測試

- 香港日期轉換、預約窗口、工作時間交集。
- 服務時長、buffer、請假和既有預約的時段計算。
- 指定員工及任何員工的候選分配。
- 套票適用性、扣減和退回規則。
- 輸入驗證和錯誤代碼映射。

### 資料庫整合測試

- 兩個併發交易不能為同一員工建立重疊預約。
- 選任何員工可在第一位衝突時分配下一位。
- 建立預約與扣套票同成同敗。
- 取消只退回一次，重複請求具冪等性。
- RLS 阻止客戶讀取另一客戶的資料。

### API 及介面測試

- 公開自費預約。
- 登入後使用套票預約。
- 時段衝突後刷新並重新選擇。
- 客戶取消及改期。
- 管理員建立員工、設定技能及排班後，可用時段立即改變。
- 非管理員不能存取後台寫入接口。

### 發佈檢查

- 完整 unit／integration／E2E 測試。
- lint、production build 和安全掃描。
- 手機與桌面瀏覽器的預約主流程。
- Vercel preview 環境使用獨立或安全的測試資料。
- 正式資料庫 migration、環境變數、管理員帳戶、網域及通知設定逐項核對。

## 14. 遷移與推出次序

1. 先新增員工、技能、排班和預約防撞欄位，不刪除現有資料。
2. 建立一位預設員工，把現有有效預約安全回填到該員工。
3. 如現有資料本身有重疊，產生報告並要求管理員處理後才啟用排斥限制。
4. 部署兼容新舊資料的讀取版本。
5. 啟用新的 availability 和交易式建立／改期／取消 API。
6. 部署新的客人預約流程和管理後台。
7. 完成 preview smoke test 後才套用正式 migration 和發佈。
8. 穩定後移除沒有路由使用的舊 Phase 2 模組和失效文件。

每個資料庫 migration 必須可重複安全檢查，並附正式環境執行前後的驗證查詢。破壞性清理會留到新流程穩定後的獨立 migration。

## 15. 驗收標準

平台只有在以下條件全部成立才視為完成：

- 客人能在手機上完整建立、查看、改期及取消預約。
- 指定員工與任何員工模式均按技能和排班顯示正確時段。
- 併發及直接 API 呼叫不能造成同一員工時間重疊。
- 套票不能被其他客戶查看或使用，扣減和退回保持一致。
- 管理員可完成日常預約、客戶、員工、排班、服務和套票操作。
- 後台所有寫入有權限驗證和審計紀錄。
- 線上站沒有假電話、待提供內容、英鎊或明顯半成品文字。
- 自動測試、production build、安全檢查及主要 E2E 流程全部通過。
- 正式 Supabase migration 和 Vercel 部署已驗證，並有回滾及營運說明。
